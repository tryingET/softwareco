# R3 reviewer answers — many-of-the-greats

Subject: [R3 RFC](resolution-rfc-r3.md) and incorporated [contract](contracts-r3.md).
Four questions come from the latest author self-inspection of R2, not a claimed
independent review. Fresh SoftwareCo-scoped Vault checks admitted many-of-the-greats
v3, first-principles v1 and second-order v1 as text-safe. No expert was consulted,
impersonated or counted as an approval signature.

## Mode 1 — strongest schools

**Giancarlo Guizzardi — category/identity correctness.** A policy decision, an actual
authorization act, a one-use permission, an execution permit, an attempt and artifact
evidence are different things. If renewing an execution permit renews permission,
the category error defeats the policy even when every local token is well formed.
A stable owner-issued identity must denote the underlying right across token aliases.
Creator authority and prospective actor identity must also stay distinct.

**Prof. Hartmut F. Binner — task/competence/responsibility congruence.** The rule's
owner controls issuance; the execution/custody owner controls admitted consumption
and follow-through under delegation. A person may hold both roles, but their acts
and responsibilities remain explicit. Execution convenience cannot transfer the
power to grant exceptions. Equally, normal continuity should not demand a new
company-policy ceremony when the original admitted attempt can be safely completed.

**Joseph Kasser — complete useful receiver outcome.** The useful thread is one
qualified inert birth followed by separately qualified agency, not an entire new
permissions platform. The scientific discriminator must actually threaten the
one-use claim: two different permits under one exception, post-partial reissue and
unknown settlement. Testing two processes with one token does not cover that threat.
A valid recovery delivers the original useful result; a new birth is a different
reserved commitment. Source/check confidence cannot prove native admission.

**Nancy Leveson — safe control under partial failure.** A replacement token, lost
reply or cleaned directory does not establish permission or nonexecution. Consumption
must precede writes, and uncertainty must block sibling permits, not only the original
process. Separate consumed permission, revocation and physical artifact/effect facts.

**Parnas — information hiding.** Define one source-owned consumption boundary and
portable references, not a new global database or atomic transaction across all
owners. The choice of actual custodian/read adapter is hidden behind a contract that
can refuse activation when it cannot supply the required evidence.

## Mode 2 — confrontation

| Clash | Incompatible assumptions | What decides it |
| --- | --- | --- |
| token uniqueness vs permission uniqueness | each permit has its own one-use budget vs all permits reference one consumed right | Guizzardi/Leveson: parent right identity and atomic reservation dominate token labels |
| execution continuity vs exception renewal | safe remaining work on original attempt vs a different start sold as recovery | Binner/Kasser: preserve original attempt only with owner-bound evidence; new attempt needs fresh O3 act |
| useful birth vs universal control platform | precise no-repeat contract vs build all identity/permission/storage services first | Kasser/Parnas: one qualified owner adapter for this boundary, no invented shipped API or platform |
| same human vs same authority act | one person can act in two roles vs an undifferentiated execution approval covers both | Binner/Guizzardi: capacities/subjects are attributable separately; O6 cannot borrow O3 power silently |

Chosen path: **contextual dominance**. Authority identity and no-repeat constraints
dominate start admission; receiver fitness favors proven same-attempt continuity;
information hiding keeps actual storage/enforcement with the existing source owner.
None of these schools supplies the missing actual owner act or native evidence.

## Mode 3 — four concrete answers

### Q1. Which owner record says the exception's start entitlement is spent?

**The authoritative consumption record for the canonical O3-issued start right.**
O3 must name its consumption custodian and supported source-native read/record
mechanism. The durable start receipt binds canonical right + O3 act/version + permit
+ original attempt + creator + subject + exact inputs + fence. O6 can be custodian
only under explicit O3 consumption delegation. Neither permit-local phase, task
state, memory nor a missing local receipt establishes availability.

This answers the required owner/subject contract; it does not claim a deployed store
or endpoint exists. Current native schema 46 reports newer decision authorization
records unavailable. The actual adapter must be qualified before issue/start; missing
custody, alias resolution, authenticity or current state blocks birth, not invents
an authority database in the Principal.

### Q2. Can O6 issue another permit against the same O3 disposition?

It may issue execution material within delegated scope, but **cannot create another
start right**. Multiple permits before consumption contend on the SAME canonical
parent; at most one start wins. After spent/held/revoked parent, a new available child
permit, alias, controller or cleaned destination admits zero new starts. Generic O6
approval—even by the same person who also holds O3—does not constitute a fresh O3 act.
Current parent identity/state and applicable guards must be checked at admission.

This is the substantive R3 change: consume the authorization slot, not just its token.
Cases G01–G06/G09/G16 expose the exact cross-permit and role-capacity bypasses.

### Q3. What authority permits a new attempt after interrupted admitted birth?

**A fresh applicable template-owner O3 exception/disposition issuing a distinct start
right**, explicitly naming old right/attempt and actual disposition. Reusing the old
O3 record with a new permit/right string is insufficient. O6 cannot renew an exception
under execution authority. The owner-native procedure governs the new reserved act;
R3 neither grants recurring birth authority nor requires a whole architecture RFC
for every safe recovery.

Fresh O3 permission also does not waive mandatory collision/source/fence/effect
conditions. If they remain unestablished, no new attempt. Known-spent history remains
spent even after artifact failure/quarantine/source rollback. Unknown settlement
holds every sibling permit; later evidence of no start is not itself retry permission.
R3 conservatively requires explicit O3 hold/replacement disposition in that case.
A known pre-start refusal, with no reservation/write, is distinct and consumes nothing.

Cases G07/G08 show fresh permission with and without the remaining required proof.
No actual fresh O3 act, parent reservation or remaining-step safety is asserted here.

### Q4. How does verification distinguish original recovery from another start?

Verify **authoritative E/P/T correlation and zero new start admissions**, not a caller's
“recovery” label. Original start must be confirmed for that exact parent/attempt;
current recovery grant, old-executor fence, unchanged subject/path/code/pin/answers
and known remaining effect/phase are mandatory. Independent native start/write logs
must show only admitted remaining work. Parent stays spent, original attempt identity
persists and no new start entitlement is issued.

A different attempt ID, blind rerender under the old label, unproved original receipt,
changed bindings or unestablished fence is not recovery. G10 is the positive fixture;
G11 is the forged/new-attempt negative. V05 requires real owner-boundary traces before
birth qualification; fixture assumptions and the retained construction checker do
not supply them.

## Nice-to-have answers and second-order consequences

- **Creator versus Principal:** existing creator C has current execution authority;
  intended inert Principal artifact/role S is separately approved as subject. S need
  not be appointed or sign its own birth. Actual Principal identity/appointment still
  precedes its activation. These are separate binding categories, not a mandatory
  different-person/actor rule: an already identified actor may hold both roles when
  its creator authority is independently current. G12/G13 distinguish that actual
  authority from persona/future-appointment claims.
- **Compact relationship diagram:** the contract explicitly shows O3 right E ->
  child permits P -> original attempt T -> artifact A, plus creator C versus subject S.
- **Reproducible construction checker:** [retained command](construction-check-r3.md)
  verifies the fixture/mapping/digest construction, never executes owner admission or
  acts as the actual birth adapter.

Second-order risk: a safety requirement can expand into another approval platform,
while token convenience can quietly expand into recurring permission. The balancing
choice is one explicit existing-owner boundary and separate actual issuer/custodian
acts, with no routine-task budget added. Observe real receiver value and complete-duty
proof; do not reward token churn, cleaned directories or static case counts.
